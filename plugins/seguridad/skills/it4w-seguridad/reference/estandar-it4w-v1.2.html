Estándar transversal · APIs y Front

Estándar IT4W: verificación de seguridad de APIs y frontends en pipelines

Versión: 1.2 · Fecha: 2026-09-30 · Alcance: todos los proyectos de IT4W: APIs / backends (.NET, NestJS/Node, Java u otros, §3 a §8) y clientes web / frontends (React, Angular, Vue y similares, §9) Origen: definido a partir de SIPRELAFT (implementación de referencia en .NET para el backend y React para el frontend). Los ejemplos cubren .NET y NestJS; el estándar es agnóstico del stack y de la herramienta de CI (los ejemplos de pipeline usan Azure DevOps).

1. Objetivo

Garantizar, de forma automática y auditable, que ningún endpoint de una API pueda ejecutar operaciones de escritura (create / update / delete) sin autenticación y autorización adecuadas, y que las lecturas estén igualmente controladas. Para los frontends, donde los permisos no se pueden hacer cumplir en el cliente, el objetivo es proteger la cadena de suministro, los secretos y los patrones inseguros del navegador (§9). La verificación debe correr en cada PR y en cada build de las ramas principales, y bloquear el merge/despliegue si falla.

Principios:

  1. Deny by default: lo que no está explícitamente permitido, está prohibido.
  2. La seguridad se prueba, no se supone: cada control tiene un test que falla si alguien lo rompe.
  3. Defensa en capas: diseño seguro + tests de autorización + SAST + SCA + secretos + DAST + revisión manual.
  4. Evidencia: cada corrida deja reportes archivados (útil para auditorías y pentests del cliente).

Una lista blanca de endpoints públicos vive en el repo (ej. security/public-endpoints.json) y se modifica solo vía PR con revisión.

3. Capa 1: Diseño seguro en el código (prevención)

3.1 Autorización global por defecto

.NET (ASP.NET Core):

csharp
builder.Services.AddAuthorization(options =>
{
    // Todo endpoint exige usuario autenticado salvo [AllowAnonymous]
    options.FallbackPolicy = new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build();

    // Políticas por capacidad, no por nombre de rol suelto
    options.AddPolicy("Escritura", p => p.RequireRole("Admin", "Operador"));
    options.AddPolicy("Lectura",   p => p.RequireRole("Admin", "Operador", "SoloLectura"));
});

Y en los controllers, escritura con política explícita:

csharp
[HttpPost]   [Authorize(Policy = "Escritura")]
[HttpDelete] [Authorize(Policy = "Escritura")]

NestJS: guard de autenticación global (APP_GUARD), rutas públicas solo con @Public(), y un guard de roles que falla cerrado en escritura (una acción POST/PUT/PATCH/DELETE sin @Roles(...) se rechaza).

ts
// public.decorator.ts
export const IS_PUBLIC_KEY = 'isPublic';
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);

// roles.decorator.ts
export const ROLES_KEY = 'roles';
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

// jwt-auth.guard.ts  (deny by default: todo exige JWT salvo @Public)
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private reflector: Reflector) { super(); }
  canActivate(ctx: ExecutionContext) {
    const esPublico = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [ctx.getHandler(), ctx.getClass()]);
    return esPublico ? true : super.canActivate(ctx);
  }
}

// roles.guard.ts  (escritura sin @Roles => 403; lectura sin @Roles => cualquier autenticado)
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(ctx: ExecutionContext): boolean {
    const req = ctx.switchToHttp().getRequest();
    const esPublico = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [ctx.getHandler(), ctx.getClass()]);
    if (esPublico) return true;
    const roles = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [ctx.getHandler(), ctx.getClass()]);
    const esEscritura = ['POST', 'PUT', 'PATCH', 'DELETE'].includes(req.method);
    if (!roles?.length) return !esEscritura;                // falla cerrado en escritura
    return roles.some((r) => req.user?.roles?.includes(r)); // 403 si no tiene el rol
  }
}

// app.module.ts
providers: [
  { provide: APP_GUARD, useClass: JwtAuthGuard },  // 1º autenticación
  { provide: APP_GUARD, useClass: RolesGuard },    // 2º autorización
]

// uso
@Post()        @Roles('admin', 'operador') crear(@Body() dto: CrearDto) { ... }
@Delete(':id') @Roles('admin')             eliminar(@Param('id') id: string) { ... }
@Get()         /* cualquier autenticado */ listar() { ... }
@Public() @Get('health')                   health() { ... }

Otros stacks: Node/Express: middleware global app.use(requireAuth) antes de montar routers; rutas públicas montadas antes desde una lista explícita. Spring: SecurityFilterChain con .anyRequest().authenticated() como última regla. FastAPI: dependencia global de autenticación.

3.2 Reglas de código

  • No confiar en IDs enviados por el cliente para determinar tenant/dueño: se derivan de la sesión/claims en el servidor (evita IDOR/BOLA).
  • Escritura solo con verbos correctos (nada de modificar datos por GET).
  • Protección CSRF en APIs con cookies (antiforgery / SameSite=Strict-Lax + token).
  • CORS con orígenes explícitos; nunca * con credenciales.
  • Rate limiting en login y endpoints sensibles.
  • Dashboards operativos (Hangfire, Swagger, actuator, métricas) deshabilitados o con autorización real en producción.
  • Errores sin filtrar detalles internos (stack traces, SQL).

4. Capa 2: Test automático de autorización (el control principal)

Un conjunto de tests de integración que enumeran todos los endpoints reales de la aplicación y verifican su comportamiento con distintos perfiles. Al enumerarse automáticamente, un endpoint nuevo queda cubierto sin escribir un test nuevo.

4.1 Matriz de verificación

PerfilEscritura (POST/PUT/PATCH/DELETE)Lectura (GET)
Sin credenciales401 (o 302 a login)401
Rol solo lectura403200 permitido
Usuario de otro tenant403/404 sobre recursos ajenos403/404 sobre recursos ajenos
Rol con permisoPermitido (sin este caso el test no distingue "bloqueado" de "roto")Permitido

Excepción: endpoints en la lista blanca pública (deben devolver lo esperado sin credenciales, y solo esos).

4.2 Reglas de los tests

  1. Fuente de verdad = la app en ejecución: enumerar con EndpointDataSource (.NET), app._router/OpenAPI (Node), RequestMappingHandlerMapping (Spring), app.routes (FastAPI) o el OpenAPI generado.
  2. Falla si hay un endpoint accesible sin auth que no esté en la lista blanca.
  3. Falla si hay un endpoint de escritura sin política de autorización explícita más allá de "autenticado".
  4. Los tests no dependen del contenido de los datos: alcanza con que la respuesta sea 401/403 antes de ejecutar lógica; ideal usar IDs inexistentes (la autorización se evalúa antes).
  5. Se ejecutan en cada PR (rápidos, en memoria o con contenedores de dependencias).

4.3 Ejemplo .NET (xUnit + TestServer) — implementación de referencia: SIPRELAFT

Patrón implementado en Siprelaft-Back y Siprelaft-Middleware. Claves del diseño:

  • La configuración de autenticación/autorización se extrae a una extensión (AddXxxAuthentication) que usan tanto Program.cs como el test. Así el test corre con la configuración real, sin duplicarla y sin base de datos ni servicios externos: un request sin credenciales se corta en el middleware de autorización antes de construir el controller.
  • Se levanta un host mínimo en memoria (UseTestServer) con los controllers reales (AddApplicationPart) y se enumeran los endpoints reales desde EndpointDataSource.
  • Se agrega un endpoint sonda sin atributos para probar la FallbackPolicy.
  • Dos archivos JSON versionados: public-endpoints.json (lista blanca) y write-endpoints.json (escrituras cuyo permiso no se declara con [Authorize(Policy|Roles)], indicando dónde se valida).
csharp
// Host mínimo con la config real de seguridad
var builder = WebApplication.CreateBuilder(new WebApplicationOptions { EnvironmentName = Environments.Production });
builder.WebHost.UseTestServer();
builder.Services.AddControllers().AddApplicationPart(typeof(AlgunController).Assembly);
builder.Services.AddMiEmpresaAuthentication(builder.Configuration, builder.Environment); // la MISMA extensión que Program.cs
var app = builder.Build();
app.UseAuthentication(); app.UseAuthorization(); app.MapControllers();
app.MapGet("/__sonda-sin-atributos", () => "publico");  // debe responder 401 por la FallbackPolicy
await app.StartAsync();
var endpoints = ((IEndpointRouteBuilder)app).DataSources.SelectMany(d => d.Endpoints).OfType<RouteEndpoint>();
csharp
[Fact] // 1. solo lo declarado es público
public void Solo_la_lista_blanca_es_AllowAnonymous() =>
    Acciones().Where(EsAnonimo).Select(a => a.Clave).Except(publicos).Should().BeEmpty();

[Fact] // 2. sin credenciales, todo responde 401 (incluye POST/PUT/PATCH/DELETE)
public async Task Sin_credenciales_nada_se_ejecuta()
{
    foreach (var a in Acciones().Where(a => !publicos.Contains(a.Clave)))
    {
        var ruta = "/" + Regex.Replace(a.Ruta, @"\{[^}]+\}", "1");
        var r = await client.SendAsync(new HttpRequestMessage(new HttpMethod(a.Metodo), ruta));
        Assert.Equal(401, (int)r.StatusCode);
    }
}

[Fact] // 3. deny by default (FallbackPolicy) probado con un endpoint sin atributos
public async Task Endpoint_sin_atributos_exige_autenticacion() =>
    Assert.Equal(401, (int)(await client.GetAsync("/__sonda-sin-atributos")).StatusCode);

[Fact] // 4. toda escritura tiene [Authorize(Policy|Roles)] o está declarada en write-endpoints.json
public void Toda_escritura_declara_su_control() =>
    Acciones().Where(a => a.EsEscritura && !EsAnonimo(a) && !TienePolicyOROles(a))
              .Select(a => a.Clave).Except(manifiestoEscritura).Should().BeEmpty();

Además, las entradas de los manifiestos se validan en ambos sentidos (una entrada sin endpoint real también falla), y cada endpoint cuyo permiso se valida dentro del controller o del handler lleva su test propio (ej. "el rol solo lectura recibe Forbid"). Esto cubre el caso "rol sin permiso de escritura → 403" sin necesitar base de datos.

Prueba de que los tests sirven (mutación): al quitar la FallbackPolicy o marcar un controller como [AllowAnonymous], los tests de arriba fallan. Conviene repetir esta verificación al adoptar el estándar en un proyecto nuevo.

4.4 Ejemplo NestJS (Jest + supertest)

Igual que en .NET: se enumeran los endpoints reales (desde los metadatos de los controllers) y se prueba cada uno con distintos perfiles. Se usa un JWT firmado con un secreto de test, sin depender del proveedor de identidad real.

ts
// test/security/endpoint-security.e2e-spec.ts
import { PATH_METADATA, METHOD_METADATA } from '@nestjs/common/constants';
import { RequestMethod } from '@nestjs/common';
import { DiscoveryService } from '@nestjs/core';
import * as request from 'supertest';
import publicos from './public-endpoints.json'; // ["GET /auth/login", "GET /health"]

const ESCRITURA = ['POST', 'PUT', 'PATCH', 'DELETE'];

function listarEndpoints(app: INestApplication) {
  const prefijo = ''; // completar si hay app.setGlobalPrefix
  return app.get(DiscoveryService).getControllers().flatMap((w) => {
    const ctrl = w.metatype as Function;
    const base = Reflect.getMetadata(PATH_METADATA, ctrl) ?? '';
    return Object.getOwnPropertyNames(ctrl.prototype)
      .filter((n) => Reflect.getMetadata(METHOD_METADATA, ctrl.prototype[n]) !== undefined)
      .map((n) => {
        const h = ctrl.prototype[n];
        const metodo = RequestMethod[Reflect.getMetadata(METHOD_METADATA, h)];
        const ruta = `${prefijo}/${base}/${Reflect.getMetadata(PATH_METADATA, h) ?? ''}`
          .replace(/\/+/g, '/').replace(/:[A-Za-z]+/g, '1').replace(/\/$/, '');
        return { metodo, ruta, clave: `${metodo} ${ruta}` };
      });
  });
}

describe('Seguridad de endpoints', () => {
  let app: INestApplication;
  beforeAll(async () => {
    const mod = await Test.createTestingModule({ imports: [AppModule] })
      // Sustituir SOLO base de datos / integraciones externas; NUNCA los guards.
      .overrideProvider(DataSource).useValue({}).compile();
    app = mod.createNestApplication();
    await app.init();
  });
  afterAll(() => app.close());

  const token = (roles: string[]) =>
    new JwtService({ secret: process.env.JWT_SECRET }).sign({ sub: 'u1', roles });

  it('sin token, todo endpoint no público responde 401', async () => {
    const fallos: string[] = [];
    for (const e of listarEndpoints(app).filter((x) => !publicos.includes(x.clave))) {
      const res = await request(app.getHttpServer())[e.metodo.toLowerCase()](e.ruta);
      if (res.status !== 401) fallos.push(`${e.clave} => ${res.status}`);
    }
    expect(fallos).toEqual([]);
  });

  it('con rol de solo lectura, toda escritura responde 403', async () => {
    const fallos: string[] = [];
    const escrituras = listarEndpoints(app).filter((x) => ESCRITURA.includes(x.metodo) && !publicos.includes(x.clave));
    for (const e of escrituras) {
      const res = await request(app.getHttpServer())[e.metodo.toLowerCase()](e.ruta)
        .set('Authorization', `Bearer ${token(['lector'])}`);
      if (res.status !== 403) fallos.push(`${e.clave} => ${res.status}`);
    }
    expect(fallos).toEqual([]);
  });
});

Notas para NestJS:

  • Ejecutar con un script dedicado ("test:security": "jest --config test/jest-e2e.json --testPathPattern security") para poder correrlo como etapa propia del pipeline.
  • El módulo se levanta con la base de datos y las colas sustituidas (overrideProvider) pero con los guards reales: lo que se prueba es la seguridad, no la persistencia.
  • Con setGlobalPrefix o versionado (/v1), completar el prefijo en listarEndpoints.
  • Como el RolesGuard de §3.1 falla cerrado en escritura sin @Roles, el segundo test también detecta una escritura a la que se le olvidó declarar roles.
  • Para tenant/dueño (IDOR), agregar un caso con dos usuarios de tenants distintos y datos sembrados en una base de pruebas (Testcontainers o SQLite en memoria).

Regla Semgrep de ejemplo (C#: acción de escritura sin [Authorize]):

yaml
rules:
  - id: escritura-sin-authorize
    languages: [csharp]
    severity: ERROR
    message: Acción de escritura sin [Authorize] ni política. Declarar autorización explícita.
    patterns:
      - pattern: |
          [$VERB]
          public $RET $NAME(...) { ... }
      - metavariable-regex:
          metavariable: $VERB
          regex: Http(Post|Put|Patch|Delete).*
      - pattern-not-inside: |
          [Authorize(...)]
          class $C { ... }
      - pattern-not: |
          [Authorize(...)]
          public $RET $NAME(...) { ... }

Regla equivalente para NestJS (TypeScript): acción de escritura sin @Roles:

yaml
rules:
  - id: nest-escritura-sin-roles
    languages: [typescript]

          metavariable: $VERB

7. Capa 5: DAST contra ambiente de pruebas

  • OWASP ZAP contra el OpenAPI/Swagger del proyecto: detecta endpoints expuestos, configuraciones débiles y headers de seguridad faltantes.
    • Baseline scan (zap-baseline.py -t https://qa.ejemplo/): pasivo, rápido, apto para correr tras cada deploy a QA.
    • API scan (zap-api-scan.py -t openapi.json -f openapi): recorre cada operación del contrato; más lento y con ataques activos.
  • Schemathesis o Postman/Newman: ejecutan cada operación del contrato sin token y con token de bajo privilegio, esperando 401/403 en escrituras y en todo lo no autorizado (schemathesis run openapi.json --url https://qa.ejemplo / newman run coleccion.json).
  • Se corre contra QA, nunca contra producción, con datos no productivos y con autorización del dueño del ambiente.
  • Se ejecuta tras el deploy a QA (no en cada PR); resultados publicados como artefacto.

8.2 Políticas de rama

  • PR obligatorio hacia main y QA, al menos 1 revisor, el pipeline de seguridad como build validation requerido.
  • Prohibido merge con checks fallidos. Excepciones solo por escrito, con responsable y fecha de vencimiento (security/exceptions.md).

9. Clientes web (Front): React, Angular, Vue y similares

Todo lo anterior protege la API. Los frontends necesitan su propio conjunto de controles, distinto porque un cliente web no puede hacer cumplir permisos por sí mismo.

Principio: ocultar un botón, deshabilitar un formulario o redirigir según el rol es experiencia de usuario, no seguridad. Quien quiera saltearse la interfaz llama a la API directamente (con curl, Postman o las herramientas del navegador). La regla "sin permiso no se puede crear, editar ni borrar" la garantizan siempre los tests del backend (§4). El frontend se protege de otros riesgos.

Excepción: frameworks con código de servidor (Next.js, Nuxt, SvelteKit, Remix: route handlers, API routes, server actions). Esa parte es backend y debe cumplir las secciones 3 y 4 como cualquier API.

9.2 Reglas de código

  • HTML dinámico: si es imprescindible renderizarlo (por ejemplo, la vista previa de un .docx convertido con mammoth, o contenido de un editor), sanitizar siempre. Ninguna librería de conversión sanitiza su salida por defecto.
tsx
import DOMPurify from 'dompurify';

// MAL: XSS si el HTML viene de un archivo o de un usuario
<div dangerouslySetInnerHTML={{ __html: html }} />

// BIEN
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />
  • Sesión: cookie HttpOnly emitida por el backend; el frontend nunca guarda el token en storage. Con cookies cross-site (por ejemplo, la app dentro de un <iframe>), SameSite=None; Secure más CORS con orígenes explícitos y protección CSRF en el backend.
  • Variables de entorno de frontend = públicas. Usar solo para URLs y flags, nunca para claves.
  • Lockfile versionado (package-lock.json) y npm ci en el pipeline, no npm install.
  • Autorización visual: ocultar acciones según rol está bien para UX, pero el backend debe rechazar la operación igual. Si la UI y la API divergen, manda la API.

9.3 Reglas de Semgrep para frontends (TypeScript/JavaScript, React)

yaml
rules:
  - id: react-dangerously-set-inner-html-sin-sanitizar
    languages: [typescript, javascript]
    severity: ERROR
    message: dangerouslySetInnerHTML con contenido sin sanitizar (XSS). Usar DOMPurify.sanitize(...).
    patterns:
      - pattern: |
          <$EL ... dangerouslySetInnerHTML={...} />
      - pattern-not: |
          <$EL ... dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(...) }} />

  - id: js-asignacion-innerhtml
    languages: [typescript, javascript]
    severity: ERROR
    message: Asignación a innerHTML/outerHTML (XSS). Usar textContent o sanitizar.
    patterns:
      - pattern-either:
          - pattern: $EL.innerHTML = $X
          - pattern: $EL.outerHTML = $X
      - pattern-not: $EL.innerHTML = DOMPurify.sanitize(...)

  - id: js-eval-o-new-function
    languages: [typescript, javascript]
    severity: ERROR
    message: eval() / new Function() ejecutan código arbitrario. Evitarlo.
    pattern-either:
      - pattern: eval(...)
      - pattern: new Function(...)

  - id: js-token-en-storage
    languages: [typescript, javascript]
    severity: ERROR
    message: Credencial o token en localStorage/sessionStorage. Usar cookie HttpOnly.
    patterns:
      - pattern-either:
          - pattern: localStorage.setItem("$KEY", ...)
          - pattern: sessionStorage.setItem("$KEY", ...)
      - metavariable-regex:
          metavariable: $KEY
          regex: (?i).*(token|jwt|secret|password|passwd|credential).*

En Angular agregar reglas para bypassSecurityTrustHtml y [innerHTML] con contenido no sanitizado; en Vue, para v-html. Las reglas en YAML con llaves ({...}) deben ir en bloques literales (|), o el archivo no parsea.

9.4 Plantilla de pipeline para frontends (Azure DevOps)

yaml
trigger: { branches: { include: [ main, QA ] } }
pr:      { branches: { include: [ main, QA ] } }
pool: { vmImage: ubuntu-latest }

stages:
- stage: Seguridad
  jobs:
  - job: Build_y_dependencias
    steps:
    - task: NodeTool@0
      inputs: { versionSpec: '22.x' }
    - script: npm ci
      displayName: Instalar dependencias (lockfile)
    - script: npm run lint
      displayName: Lint
    - script: npm run build
      displayName: Type-check y build
    - script: npm audit --audit-level=high
      displayName: SCA (npm audit)                      # BLOQUEANTE High/Critical
    - script: |
        archivos=$(git ls-files | grep -E '(^|/)\.env(\.|$)' | grep -viE '\.(example|sample|template)$' || true)
        if [ -n "$archivos" ]; then echo "##vso[task.logissue type=error]Archivos .env versionados: $archivos"; exit 1; fi
      displayName: Sin archivos .env versionados       # BLOQUEANTE

  - job: Secretos_y_SAST
    steps:
    - checkout: self
      fetchDepth: 0
    - script: |
        curl -sSfL https://github.com/gitleaks/gitleaks/releases/download/v8.21.2/gitleaks_8.21.2_linux_x64.tar.gz | tar -xz gitleaks
        ./gitleaks detect --source . --redact --exit-code 1
      displayName: Secretos (Gitleaks)                 # BLOQUEANTE
    - script: |
        pip install semgrep
        semgrep scan --config security/semgrep --error src
      displayName: SAST (Semgrep)                       # BLOQUEANTE

Si el proyecto tiene un hallazgo conocido que aún no se puede corregir, el paso de Semgrep puede llevar continueOnError: true de forma temporal y documentada, con el hallazgo registrado en el README del proyecto y una fecha para volverlo bloqueante.

9.5 Complementos opcionales

  • Tests E2E (Playwright/Cypress) que verifican que, con un usuario de solo lectura, la interfaz no ofrece acciones de escritura. Es un control de UX; no reemplaza los tests del backend.
  • DAST (ZAP baseline) contra el sitio en QA para validar headers y CSP.
  • Análisis de licencias y de tamaño del bundle si el cliente lo exige.

9.6 Qué NO cubre este control

Un pipeline de frontend no puede demostrar que la aplicación respeta los permisos: eso solo lo prueba el backend (§4). Tampoco detecta lógica de negocio insegura en el cliente ni compromisos de la cadena de suministro que aún no figuren en las bases de vulnerabilidades.

10. Checklist para PR

  • Todo endpoint nuevo declara su política de autorización (o está en la lista blanca pública, justificado).
  • Endpoints de escritura con permiso específico, no solo "autenticado".
  • Recursos filtrados por tenant/dueño desde la sesión.
  • El test de autorización pasa y cubre el endpoint nuevo.
  • Sin secretos ni credenciales en el diff.
  • Sin dependencias nuevas con vulnerabilidades High/Critical.
  • Cambios en auth/roles/CORS/cookies revisados por otro desarrollador.

Solo frontends (§9):

  • Ningún dangerouslySetInnerHTML / innerHTML / v-html / bypassSecurityTrust* con contenido sin sanitizar.
  • Sin tokens ni credenciales en localStorage/sessionStorage; sin claves en variables de entorno del frontend.
  • Sin archivos .env con valores reales versionados.
  • El lockfile está actualizado y npm audit no reporta High/Critical.
  • Ocultar una acción en la UI no reemplaza la validación en el backend (el backend rechaza la operación igual).

11. Incorporar un proyecto nuevo (pasos)

  1. Configurar autorización por defecto (sección 3.1).
  2. Crear security/public-endpoints.json con la lista blanca mínima.
  3. Copiar/adaptar el test de inventario de endpoints (sección 4) y etiquetarlo Category=Security.
  4. Agregar el pipeline de seguridad desde la plantilla (sección 8.1).
  5. Configurar la política de ramas con el pipeline como requisito.
  6. Documentar en el README del proyecto: roles, políticas y endpoints públicos.
  7. Coordinar con el cliente el ambiente para DAST y la frecuencia del pentest.

Frontend nuevo: copiar la plantilla de la sección 9.4 y las reglas de la 9.3 (security/semgrep/), verificar que .env no esté versionado y configurar la política de ramas con el pipeline como requisito.

13. Limitaciones

Estos controles reducen mucho el riesgo pero no lo eliminan: no detectan fallos de lógica de negocio complejos ni autorización a nivel de fila mal implementada más allá de los casos modelados. Se complementan con revisión manual y un pentest periódico.
